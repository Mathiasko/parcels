# Decision log — self-hosted parcel tracker

Every ruling made during implementation, in the order made, with what it costs
if wrong. Extracted from the subagent-driven-development ledger before that
scratch workspace was removed. The spec and plan hold the design; this holds the
decisions taken *during* the build, including several corrections to the spec and
plan themselves.

Preserved 2026-10-27. 76 rulings.

- Ruling: adapters NEVER touch `src/carriers/registry.ts` — each only exports its adapter const; Task 11b performs all five registrations centrally. Why: five tasks editing one file is the plan's only real write-conflict, and central registration is the explicit later task. Cost if wrong: `detectCarrier` returns nothing until T11b lands, so T5–T11 adapter tests must construct adapters directly rather than via the registry.
- Ruling: `src/db/messages.ts` is created by Task 16 with READ helpers only (`unparsedMessages`, `messageById`); Task 17 appends the WRITE helpers (`storeMessage`) to that same file. Why: the plan orders the `/attention` page before IMAP ingest, and the `messages` table already exists in the Task 2 schema, so the read path has no dependency on IMAP. Cost if wrong: a small merge of two helper sets in one file — no interface change.
- Ruling: dispatch is SEQUENTIAL, never parallel implementers, despite the user's "parallelise the adapters" framing. Why: the skill forbids parallel implementers because they collide on git index and shared files, and all five adapters commit to one branch. Orchestration is preserved via batching (below). Cost if wrong: longer wall-clock; no correctness risk.
- Ruling: batch tightly-coupled tasks into single dispatches — [T1-T4], [T6-T7], [T11+T11b], [T12-T13], [T15-T16], [T17-T18] — 12 dispatches instead of 19. Why: the skill's own batching guidance, and interface drift is the main risk when consecutive tasks define and consume the same signatures. Cost if wrong: a larger diff per review, so a reviewer may surface more findings per round.
- Ruling: spec §7 defines exactly 5 tables; the brief's "five plus raw_responses" was a plan wording error. No sixth table. Cost if wrong: none, schema matches spec.
- Ruling: accept the implementer's `earlierOffsetInFold` fix and reject the plan's claim that Luxon picks the earlier offset by default. Reviewer probe showed Luxon's fold result is time-of-run dependent (inherits the offset in force "now"), so the plan's test would pass in summer and fail in winter. Cost if wrong: DST fold timestamps off by one hour twice a year.
- Ruling: accept `StoredEvent` (= ParcelEvent + id + parcelId) as a new exported type from src/db/events.ts, not in the plan. markNotified needs ids. Later tasks import it from there. Cost if wrong: a rename across the db and notify layers.
- Ruling: accept `build` = `tsc && cp src/db/schema.sql dist/db/schema.sql`. Plain tsc does not copy the .sql that openDb reads at runtime, so the launchd entry points would crash without it. Cost if wrong: none; it is additive.
- Ruling: spec §6.1 under-specified the events[] field names, so the implementer invented `description`, `zip`, `lat`, `lon`. Amended the spec (commit 6c44a4a) to record the verified names (`detailDescription`, `postcode`, no coordinates at all) and sent the code fix to the implementer. Cost if wrong: posta pickup data parses as undefined against the real API, silently.
- Ruling: unmapped detailCode falls through to the stateCode mapping, NOT to unknown — plan wins over the spec's ambiguous wording; spec amended (commit 2825213). Why: detailCode appears on many ordinary events, so erasing a known stateCode would degrade healthy parcels. Cost if wrong: ordinary parcels show as in_transit when a rare detail code actually meant a problem.
- Ruling: a date-only retainedTill means END of that day in Europe/Bratislava, not midnight at its start; spec amended. Why: the parcel is collectable during that day. Cost if wrong: the 48h pickup reminder and expiry fire up to 24h early.
- Ruling: matches() SHOULD enforce the S10 check digit, against the spec's "validate locally to catch typos only" phrasing. Why: the API ignores the check digit, so a well-formed typo returns ok with empty events and would sit at pre_transit forever. Local rejection is the only place a typo can be caught. Cost if wrong: a valid inbound S10 number with an unusual check digit fails carrier detection and needs manual carrier selection.
- Ruling: non-200 from posta maps to `transport`, not `gated`. Why: keyless official API with no credential to rotate. Cost if wrong: a persistent posta 403 looks like a network problem rather than a broken adapter.
- Ruling: the registry stays empty only until an adapter exists. Task 6/7 registers `posta` (the sole existing adapter) so the CLI's auto-detect tests are real; Task 11b registers the remaining four and asserts all five. Why: keeping it empty would force the CLI detect tests to use stubs, testing plumbing instead of behaviour. Cost if wrong: a trivial move of one register() call.
- Ruling: a batch-level parse/transport failure must NOT change parcel status; only a single-parcel chunk marks that parcel `unknown`. Why: the spec sentence "mark the parcel unknown" assumed one parcel; applied to a 100-number posta batch it flips the whole dashboard to unknown and drops ready_for_pickup parcels out of their every-slot tier. Cost if wrong: a genuinely unparseable single parcel keeps a stale status instead of showing unknown.
- Ruling: backoff tiers keyed on lastPolledAt age (~20h daily, ~2.5h medium), not on slot index. Why: this Mac is asleep ~41% of the time, so sleeping through 07:00 skipped the daily tier for the whole day, and a Mac awake only in hours 8-9/11-12 never polled the every-third-slot tier at all. My plan's "at the first slot" wording caused it. Cost if wrong: slightly irregular poll spacing versus the nominal hourly grid.
- Ruling: on an all-`transport` chunk the orchestrator stores the captured body once and records health, rather than relying on the adapter to throw. Why: posta's never-throw contract made the raw_responses escape hatch unreachable for the only real adapter. Cost if wrong: a little extra raw-body storage on transient network failures.
- Ruling: my round-1 instruction to key backoff tiers on lastPolledAt was itself a defect — lastPolledAt only advances on a real answer, so every failing parcel became due every slot (a 7-day-idle parcel went from 1 poll/day to 15). Correct design: add last_attempted_at, stamped on every attempt, and key the gaps on max(lastPolledAt, lastAttemptedAt), keeping lastPolledAt as "last real answer" for the UI. Cost if wrong: either retry storms against two Disallow:/ hosts, or a recovering parcel waits up to 20h for its next poll.
- Ruling: runPoll must consult carrier_health and skip a `gated` carrier until now-lastErrorAt exceeds min(2^(n-1) h, 24h), sending one canary parcel while skipped. Why: nothing capped anything, so a rotated SPS key meant hourly hammering of a known-broken endpoint that serves Disallow:/ — spec §6.6 forbids exactly this. Cost if wrong: recovery from a carrier outage is detected up to 24h late.
- Ruling: a needs_postcode parcel must not call the carrier at all while its postalCode is empty; it also must not record health `ok`, nor overwrite a real carrier statusDetail. Why: deterministic failure that can never self-correct by retrying. Cost if wrong: GLS/DPD parcels missing a postcode never retry even after one is supplied, if the flag-clearing is wrong.
- Ruling: the gated canary IS the throttled probe, not an addition to the skip. My round-2 wording produced one canary per hour indefinitely, which defeats the exponential window for exactly the two Disallow:/ hosts the backoff protects. Correct: zero requests while the window is open, exactly one canary when it elapses, full fan-out only after a canary succeeds. Cost if wrong: carrier recovery detected up to 24h late.
- Ruling: add a startup column guard (PRAGMA table_info) since openDb runs schema.sql with IF NOT EXISTS on tables — a pre-existing parcels table would silently lack last_attempted_at/needs_postcode and fail at query time. Cost if wrong: one extra startup check.
- Ruling: the needs_postcode flag must record WHICH postcode was rejected, not a bare boolean. Round 3 clears the flag whenever postal_code is non-empty, but `cli add` stamps defaultPostalCode on every parcel, so the flag self-clears every run and the every-slot retry storm returns the moment GLS lands. Fix: store the rejected postcode; skip while it still equals the current one; clear only when the postcode actually changes. Cost if wrong: GLS/DPD parcels either hammer the carrier every slot, or never retry after the user fixes the postcode.
- Ruling: round 4 uses a fresh implementer one model tier up, per the skill's mechanical rule. Noting honestly that rounds 1-3 each fully addressed their findings — the loop length came from my own two bad instructions (lastPolledAt keying, hourly canary) plus newly-surfaced latent issues, not implementer failure. Cost if wrong: a fresh context re-reads code the prior agent already knew.
- Ruling: the one residual finding (a legacy DB from intermediate commits 72b3b00/615d9b7 would pass the name-only schema guard but carry needs_postcode as INTEGER, throwing NOT NULL on every run) is PARKED rather than fixed. Verified no data/ directory or parcels.db exists anywhere in the repo, so the precondition cannot occur. Cost if wrong: none today; if someone restores an old DB file they get a confusing per-run parse failure instead of a clear message.
- Ruling: spec §6.2 under-specified Packeta's `item` field names, same gap as §6.1. Amended (commit 74318e6) from recon: barcode, packetStatusId (string), packetStatus, sender, branchAddress (a plain STRING), courierId, trackingDetails[{text,time}]; no delivered-at, no ETA, recipient never named. The implementer's guesses turned out correct. Cost if wrong: none now.
- Ruling: parcels.status must come from the adapter's authoritative top-level status, NOT from the newest event; spec §7 invariant 3 amended (commit 282be4f). Why: stored events are never restamped (ON CONFLICT DO NOTHING, dedupHash excludes status), so for prose-only carriers (Packeta, SPS) a status change arriving without a new trackingDetails entry is reverted on EVERY poll — leaving status=in_transit beside status_raw="ready for pickup" and a populated Z-BOX pickup point, healing only if the carrier later adds an entry. It also blocked the retroactive mapping fix §5 rule 3 promises. delivered_at still comes from the newest event's timestamp. Cost if wrong: a sloppy adapter's top-level status is no longer masked by event-derived recompute.
- Ruling: spec §6.3 listed GLS's error CODES but never the field carrying them — the implementer guessed `exceptionCode`; recon verified `lastError`, and the 403 body has no lastError at all. Amended (commit 7e1a921) with all three live error envelopes plus the rstt028 record field list from GLS's client code. Cost if wrong: every GLS error misclassified, so unknown parcels look like transport failures.
- Ruling: GLS must NEVER return needs_postcode — it degrades to rstt029 status-only instead. Why: rstt029 needs no postcode and gives an authoritative status, but a needs_postcode result makes the orchestrator skip that parcel on every future poll. The brief's own test was wrong: it would have made the app silently refuse to track a parcel it can track. Spec amended. Cost if wrong: GLS parcels without a postcode show status but no event history (acceptable and visible).
- Ruling: the needs_postcode FetchResult variant and its orchestrator machinery (built over rounds 2-4 of Task 6-7) have NO v1 caller — both postcode-dependent carriers degrade instead. Keeping it: it is built, tested, cheap, and a future carrier may genuinely need it. Flagging honestly as over-build for the final review to triage. Cost if wrong: dead code the final reviewer may want removed.
- Ruling: a 400 fieldExceptions on `zipcode` (malformed postcode) also degrades to rstt029 status-only, not `transport`. Why: it is a deterministic failure that would retry forever against a carrier we treat politely — the same class as E609, just caught by input validation. All three postcode problems (absent, mismatched, malformed) now behave identically. Other fieldExceptions attributes stay `transport` — no evidence about them. Cost if wrong: a malformed-postcode parcel shows status but never history, instead of surfacing as a failure.
- Ruling: which addresses[] entry is the parcel shop is unverifiable without a live INPICKUP capture; the adapter takes the first entry with coordinates. Added to spec §15's first-real-parcel confirmations. Cost if wrong: a GLS pickup point shows the wrong address or coordinates.
- Ruling: amended spec §6.4 with SPS's verified response envelope and field names BEFORE dispatching Task 10, to stop the recurring gap (five sections named values without naming the field holding them, costing a fix round on three of four adapters so far).
- Ruling: the scraped-key cache must be module-level with a TTL, not a WeakMap keyed on the HttpClient. Why: poll.ts and cli.ts wrap the client with captureBodies ONCE PER CHUNK, so with batchSize:1 every parcel gets a fresh wrapper object and the cache missed every time — and its test passed only because it reused one stub, giving false confidence. Cost if wrong: 2 extra GETs per SPS parcel per poll.
- Ruling: captureBodies must truncate each recorded body (64 KB). Why: it records every response, so on an all-transport chunk poll.ts stored the index HTML and the ENTIRE minified JS bundle into raw_responses, which exists to diagnose status mappings. Shared-code change affecting all adapters. Cost if wrong: a genuinely large useful body gets truncated mid-diagnosis.
- Ruling: amended spec §6.5 with DPD's exact Firebase headers and Remote Config body before dispatching Task 11 (the section named endpoints but omitted them), and with the same degrade-not-refuse rule as GLS: no postcode -> continueWithoutVerification=true, never needs_postcode.
- Ruling: the DPD auth cache must PERSIST to a file under the data dir, not just module memory. Why: the poller is short-lived and exits every run (spec §4), so the ~5h token and 24h credential TTLs never survive — every hourly run re-ran the whole Firebase+OAuth chain and minted a NEW Firebase installation id (~15/day), which is odd client behaviour and a plausible abuse trigger. The brief required persistence; the implementer followed the SPS in-memory pattern instead. Cost if wrong: an extra file to manage, and a stale persisted token costing one retry.
- Ruling: a bare 404 must require the PARCEL_NOT_FOUND discriminator, else `transport`. Why: a Cloudflare/gateway 404 or a moved API path would be silently reported as a normal missing parcel and raise no alarm — precisely the quiet failure mode this adapter is most at risk of. Cost if wrong: a genuine 404 lacking the field alarms instead of reporting not_found.
- Ruling: the Firebase Remote Config body (the Basic credential) and the OAuth body (access token) must never reach raw_responses. captureBodies records every response in the chunk and poll.ts stores them on failure. Low risk (local gitignored DB, app-wide not personal secret) but a diagnostics table is the wrong home for live credentials. Cost if wrong: a redaction deny-list that hides a body someone wanted for diagnosis.
- Ruling: upheld the implementer's decision NOT to hardcode a fallback Basic credential, against the SPS precedent. Why: §6.5 forbids it, and a stale literal gives a 401 loop ending in `gated` with an alarm, whereas a Firebase outage gives quiet retried `transport`. SPS's fallback is a public build constant; DPD's is a rotating secret. Persistence (Important 1) is what actually buys outage tolerance. Cost if wrong: a Firebase outage blocks DPD until it recovers.
- Ruling: in `auto` mode a terminal-notifier permission failure (exit 3) must fall back to osascript, remembered per process. Why: as built, auto picks terminal-notifier because the binary exists, every send exits 3, send() resolves, and NOTHING is delivered — the app's entire reason for existing silently does nothing until an undocumented manual step. An explicit terminal-notifier mode still fails loudly. Cost if wrong: notifications post as "Script Editor" with no click-through until the user authorises.
- Ruling: gated/transport carrier alarms are sent OUTSIDE the summary count. Why: the alarm was stamped notified_at, then folded into a 200-char-truncated summary string as the LAST entry, so with 6+ updates a "your tracking is broken" alarm was recorded as sent and never displayed, and not repeated until recovery. Cost if wrong: one extra banner during a carrier outage.
- Ruling: add a `last_announced_status` column to parcels; compare against it rather than an in-memory before-snapshot. Why: transitions existed only as "status changed during this run", gated on `if (deps.notifier)`, so any caller without a notifier (the planned web Refresh button, email ingest) silently consumed the transition. Also fixes transient-unknown re-announcement. Cost if wrong: one more column and a slightly staler notion of "announced".
- Ruling: the osascript path switches to `on run argv` with a `--` separator, resolving the spec-vs-brief conflict in favour of the spec. Why: spec §10 and Global Constraint 9 forbid interpolating untrusted text into an AppleScript literal; escaping is defence, argv is the absence of the problem. Reviewer verified the form, including that osascript parses a leading -x value as an option without `--`. Cost if wrong: none; it is strictly safer.
- Ruling: implement spec §12's transport-failure alarm at 3 consecutive failures, SUPPRESSED when every carrier failed in the same run. Why: a permanently-timing-out carrier otherwise freezes every parcel on it with no trace but a page nobody opens — silent staleness is the worst failure for a proactive tracker. The suppression avoids five "carrier down" banners every hour on a flaky connection. Cost if wrong: a genuine simultaneous five-carrier outage goes unannounced.
- Ruling: the terminal-notifier leading-character escape must also cover leading whitespace and zero-width characters. Reviewer probed the real binary: " (x)", "\t(x)", NBSP+"(x)", U+200B+"(x)" are all rejected (exit 2/4). Carrier text like " (Redirected)" would silently drop the banner. Cost if wrong: a stray backslash visible in a banner.
- Ruling: that detour exposed a real coverage gap — 315 tests never executed the built entry point, so a runtime failure in the real binary was invisible. Kept the debug agent's regression test (commit 2e604f8, test/built-binary.e2e.test.ts) which spawns dist/cli.js as a child process with a temp config and temp DB. Cost if wrong: it skips silently when dist/ is absent, so a fresh clone never runs it.
- Ruling: reworded spec invariant 0, which overclaimed "None of it lives in memory". A repeat failed delivery attempt is still derived from in-memory events and is not durable; also documented that stamping before sending makes delivery at-most-once by design. Cost if wrong: none, it is a doc correction.
- Ruling: sleep detection uses `sysctl -n kern.waketime`, not a clock delta. My plan told implementers to diff monotonic clocks; I verified process.hrtime.bigint() reads 434.56h here, identical to os.uptime() and wall-time-since-boot, so it INCLUDES sleep and the gap always measured ~zero. The reconnaissance's CLOCK_UPTIME_RAW trick works only from C. The implementer's os.cpus() tick-mean proxy was resourceful (within 0.3%) but kern.waketime is exact, cheap and purpose-built. Spec §9 amended (commit 11b021b). Cost if wrong: no forced refresh after a long sleep, so the first poll of the day uses normal tiers.
- Ruling: a forced refresh overrides the PER-PARCEL TIER BACKOFF ONLY — never the gated-carrier throttle or the needs_postcode skip. My brief omitted this. Why: those two exist to stop retry storms against the two Disallow:/ hosts; a refresh that bypassed them would mean every lid-open hammers a known-broken endpoint with every parcel at once, reintroducing in one line a bug that took three fix rounds to remove. Cost if wrong: a gated carrier's recovery is noticed up to 24h later than a refresh would notice it.
- Ruling: accepted that "long gap" effectively means "first run of the day" (a 21:00-07:00 sleep always trips a 6h threshold). Documented in spec §9 rather than tuned. Why: the most valuable moment for fresh data is when the lid opens, and with Important B the cost cannot become a storm.
- Ruling: REVERSE my earlier endorsement — the implementer's kern.sleeptime addition must be reverted. I verified live: waketime 18:47:34 vs sleeptime 18:47:18 is a 16-SECOND gap, because both sysctls track the LATEST transition and this Mac logged 419 DarkWake entries today. Sleep-to-wake arithmetic therefore measures maintenance cycles, so a real 21:00-07:00 sleep never reaches the 6h threshold and the feature never fires. Correct model is wake-minus-last-poll (~10h, trips as intended). A DarkWake counting as a wake is acceptable: an occasional extra refresh is bounded, missing every real sleep is not. I endorsed the addition in a user-facing message before checking it — corrected to the user. Cost if wrong: a slightly-too-eager forced refresh after maintenance wakes.
- Ruling: the reboot branch (bootMs > waked) is dead code — the early `waked === undefined` return precedes it and a wake cannot predate boot. Remove branch and claim; a reboot sets a fresh baseline on the first run anyway. Cost if wrong: none.
- Ruling: src/.DS_Store was committed (confirmed tracked); remove from the index and gitignore.
- Ruling: recordPoll throwing must not turn a successful poll into exit 1, and the last_poll SELECT must be inside the try.
- Ruling: ingest must be STRICTLY READ-ONLY and never write IMAP flags. The original design fetched UNSEEN and set \Seen after commit — harmless on a throwaway mailbox, but on the user's main account it would silently mark their own email as read. Dedupe on messages.message_id instead. Cost if wrong: re-processing the same message, which the UNIQUE constraint already absorbs.
- Ruling: config.json was 644 holding a live App Password; chmod 600 applied.

The live API answers the SK form in full but our regex rejected it (matches:false, detectCarrier:[]), and every SPS parcel in this user's mailbox uses that form. UPS/DHL entries stay excluded. Fixed in commit 3837995, 380 tests. Cost if wrong: a real SPS number containing I or O still fails detection (the published class excludes them).
- Ruling: POST /refresh SHOULD force, scoped to what the user pointed at — per-parcel: forceAll + parcelIds:[id]; global: forceAll + parcelIds computed as active, not dormant, lastAttemptedAt > 60s. Why: a refresh button that reports "Nothing was due" is a broken affordance, and the throttles still apply; but forceAll skips isDue entirely, which also bypasses the DORMANT check, so an unscoped global force would poll every 30-day-dead parcel. Cost if wrong: a user can generate a little load by clicking, bounded by the mutex and the carrier throttles.
- Ruling: extract a shared initRuntime(config) called by poll.ts, cli.ts and server.ts, replacing three hand-copied setDpdAuthStore calls, plus a test that a stubbed DPD token fetch writes dpd-auth.json beside a temp DB. Why: the wiring was correct in all three but nothing would fail if any line were deleted. Cost if wrong: a small indirection in three entry points.
- Ruling: DPD must map a success-shaped empty shell (no `status` object, no parcelHistory/parcelEvents) to not_found, keyed on the ABSENCE of `status` rather than on parcelSearchType. - Ruling: archived-on-arrival parcels must appear in /history. ## Deferred minors still open at merge

- `npm run typecheck` is opt-in; not wired into `npm test` or prebuild, so test/ typing only checked on demand.
- retryAfterMs passes odd strings ("-5", "1e3") to Date.parse; clamped to 0-60s so harmless.
- http client now buffers every response body eagerly, including final 429/5xx.
- while still ready_for_pickup, pickup/retainedTill can fall back to an older event, so a re-notification could surface a stale office/deadline. Real-API-shape question for the first live parcel.
- console.warn fires per unmapped-stateCode event; no logger in the repo yet.
- no test pins retainedTill in CET (winter); code verified zone-correct by reviewer probe.
- no savepoint per parcel, so one unstorable result rolls back that whole carrier's transaction each run (visible as health `parse`).
- a parcel stuck in ready_for_pickup polls every slot forever if the carrier never emits `returned`; needs an age cap.
- spec §12's not_found attempt counter is not implemented.
- dormancy is derived inside isDue and never persisted, so the /attention page must recompute it.
- the column/field name `needsPostcode` holds a postcode string with '' meaning "rejected with none"; a future `if (p.needsPostcode)` reader would misread '' as unflagged.
- under the mid/slow tiers a corrected postcode can still wait up to 2.5h/20h because the earlier attempt stamp counts.
- the UI must not render a status chip for an event with no `code` and status `unknown` — faithful to prose-only carriers, but it would look like data loss.
- src/carriers/packeta.ts:55 comment still claims the DB re-derives status from the newest event; the fix made that false.
- delivered_at from the newest event's timestamp is an approximation when a carrier flips to delivered without emitting a new event; spec does not mention it.
- delivered_at clearing is effectively unreachable in production since terminal parcels are never re-polled, so the retroactive mapping fix applies only to still-active parcels.
- if addresses[] has entries but none carry coordinates, toPickup now drops name and street, where the pre-fix code kept parcelShop.name.
- no test for a parcelShop without coordinates returning {kind:'parcelshop'}; zipcode case-insensitivity untested.
- a bad states[].time degrades the whole SPS result to `transport`, discarding the authoritative shipmentStatus over a display-only field. Kept for consistency with Packeta and GLS; a loud failure is arguably right while the format is unobserved. Keeping status + dropping only unparseable events would be strictly better.
- a wrongly-captured key string is used unvalidated, yielding a 401 and a gated alarm with no retry against the known literal.
- the 64 KB cap counts UTF-16 units, so a slice can split a surrogate pair.
- the first chunk's capture wrapper still records the index page and first 64 KB of bundle on a scrape, which can reach raw_responses if that chunk fails.
- no poll-level test asserting raw_responses contains no credentials; the mechanism is proven at captureBodies but nothing pins that poll.ts uses the default deny-list, so a future edit passing [] there would leak silently.
- redaction is blanket and ignores status, so Firebase/OAuth ERROR bodies are also redacted — exactly the text you would want after a Remote Config shape change. Redacting only 2xx would keep error detail.
- when scans exist and milestones() throws, the whole history is dropped rather than the one malformed entry, so a real PARCEL_HANDED hand-off could silently resolve as pre_transit.
- no cold-start-with-persisted-token-then-401 test; future-dated at/expiresAt in the auth store never expires; stale tmp file left if rename fails; no milestone-path tiebreak test.
- the poller never tells the user terminal-notifier is unauthorised — only `notify-test` does.
- notify-test exits 0 for terminal-notifier exit codes 2/4 (rejected arguments), only the "check a banner appeared" line hints at it.
- offline suppression needs 2+ carriers touched in the same run, so a lone due carrier in an offline run still alarms after 3 failures.
- one notified_at serves both gated and stale alarms, so a carrier going stale then gated in one outage gets no escalated second alarm.
- e2e test skips silently and will test a stale dist/; its third test name mentions `show` but only checks `list`.
- the offline guard needs 2+ carriers touched in a run, so with the user's usual 0-1 active carriers an offline Mac still produces one false "Mail ingest is failing" banner after 3 runs (self-clears).
- per-message ingest failures are only logged — recordIngest still records "ok", and a poison message is silently re-downloaded every hour with no /health or /attention surface.
- the linear stripBlocks fix means an unclosed <head>/<style> now swallows the rest of the mail (previously the text survived); a fragment with an unclosed opener loses its number and goes to needs-attention.
- /history labels a parcel "archived" whenever delivered_at is missing, so a delivered parcel with NULL delivered_at would mislabel.
- PHONE_LABEL `tel\w*` also matches inside words like "hotel"; PHONE_PREFIX can demote a real GLS number starting 420/421.
- no test mixes a delivered and an archived parcel on one carrier to check the median's n numerically.

## The Mac app (2026-10-29 to 2026-10-30)

The rulings made while building the Mac app (plan `docs/superpowers/plans/2026-10-29-mac-app.md`,
spec `docs/superpowers/specs/2026-10-29-mac-app-design.md`), numbered as in that build's ledger,
then the decisions Task 12's end-to-end update forced.

- Ruling R1: all work happens in a separate git worktree, never in the main checkout. Why: the live launchd install runs the main checkout's `dist/` and `node_modules/`, so building there would swap code under the running tracker. Cost if wrong: none; a worktree only isolates.
- Ruling R2: Task 7 may change `src/core/app-host.ts` (from Task 5), to fill the dashboard's app dependencies from the environment and to turn a staged update into "installed" at startup. Why: the plan says the app host fills them but left the file out of that task's list. Cost if wrong: none.
- Ruling R3: the main process passes `PARCELS_RESOURCES` as `process.resourcesPath` when packaged and the repository root (`app.getAppPath()`) in a dev run. Why: unpackaged, `process.resourcesPath` is Electron's own folder, which has no `gmail-filter.xml` or certificate hash. Cost if wrong: dev runs 404 the filter download.
- Ruling R4: the repository's `node_modules` stays on Node's ABI; Electron-ABI native builds happen only inside the packaged app, and any builder step that rebuilds better-sqlite3 in place must restore it. Why: vitest and the git install use that `node_modules`. In practice better-sqlite3's N-API prebuild loads in both, so nothing is rebuilt (`npmRebuild: false`). Cost if wrong: either vitest or the app crashes on a module-version mismatch.
- Ruling R5: the spike automates what it can; whether Calendar and notification permissions survive a re-signed rebuild needs a person to click Allow, so it moves to the author's hand check. The signing script runs without prompts. Cost if wrong: Calendar may ask again after an update, an annoyance rather than a failure.
- Ruling R6: signing follows the spike: `mac.identity: null` and an afterPack hook that signs with "Parcels Signing" through @electron/osx-sign (no identity validation, no timestamp); the RunAsNode fuse off; `npmRebuild: false`; and the swap script opens the app with `ELECTRON_RUN_AS_NODE` unset. Why: electron-builder refuses an untrusted self-signed identity, and with RunAsNode on, an inherited `ELECTRON_RUN_AS_NODE` turns the app into plain Node. Cost if wrong: unsigned or broken builds, which the smoke test catches.
- Ruling R7: setup and the update scripts were to export `ELECTRON_SKIP_BINARY_DOWNLOAD=1` before `npm ci`. Task 11 found it unnecessary and did not add it: Electron 45 has no install script and downloads its binary on first use, never during `npm ci`. Cost if wrong: slower friend installs only.
- Ruling R8: the app's notifier treats a message the main process never received as a failed delivery. Why: a silent drop would hide a missing channel and mark the banner as sent. Cost if wrong: none.
- Ruling R9: the app polls once at startup when a scheduled slot was missed while it was not running, and a timer that fires a moment early counts as its slot. Why: an update restart or a crash restart must not skip a poll, and an early timer must not poll the same slot twice. Cost if wrong: one extra poll at launch.
- Ruling R10: a staged update must be Parcels's bundle id at exactly the version asked for, not only signed by the right certificate. Why: the certificate signs every build ever made with it, so an older Parcels with a known flaw, or the spike app, would otherwise pass as the update. Cost if wrong: a little extra code.
- Ruling R11: the startup catch-up runs only when a poll is on record. Why: every case that matters (move in, update restart, crash restart) has one, and a fresh install with no mail yet would otherwise poll on every first start. Cost if wrong: a fresh install's first poll waits for the next slot unless Refresh is pressed.
- Ruling R12: a notification's click opens the path of a loopback dashboard URL, and anything else opens the dashboard's home. Why: the server sends full loopback URLs, so a rule of "must start with /" would send every click home. Cost if wrong: none.
- Ruling R13: the move-in task also takes the main-process fixes the menu-bar review found: a startup failure shows an error and exits, uncaught exceptions are no longer swallowed, a second launch is caught from the start, logout quits cleanly, and a failed move in removes only what it created. Why: a failed move in that removed the whole support folder would also remove Chromium's state and the move-in marker. Cost if wrong: small extra scope.
- Ruling R14: three move-in review points were fixed at once rather than deferred: only jobs actually stopped are started again, a move in cut off by a crash is finished at the next launch, and the result page is honest when the rollback itself failed. Why: each guards against a friend ending up with no install running, two installs running, or a false statement. Cost if wrong: small extra scope.
- Ruling R15: the swap fixes sweeping `Parcels.app.old-<version>` leftovers and recognising the app's process by any path ending in `Contents/MacOS/Parcels`. Why: junk left in Applications and a swap started too early are both things a user sees. Cost if wrong: small scope.
- Ruling R16: `PARCELS_RELEASES_URL` overrides the release feed (the `releases/latest` JSON, with the files fetched from beside it) only in an unpackaged run or in a bundle whose package.json carries `parcelsDevReleases: true`, set only with `electron-builder -c.extraMetadata.parcelsDevReleases=true`. The main process decides, passes the variable to the server only then and removes it otherwise; `build-release.sh` and `check-release-zip.mjs` refuse any bundle that names the flag. Why: the end-to-end update needs packaged builds, and a release must never follow a feed whoever sets an environment variable could choose. Cost if wrong: one extra flag check in the release path.
- Ruling R17: the end-to-end update runs build A (0.90.0) with `PARCELS_SMOKE=1` and a temporary HOME, and drives Check, Update now and Restart over HTTP, with the same POSTs the Health buttons send; versions come from `-c.extraMetadata.version`, never prerelease versions and never a change to package.json. The relaunched app must be shown to run under the temporary HOME. Why: the buttons are thin forms over those routes, the screenshots cover the page, and the real `~/Library` must stay untouched. Cost if wrong: none.
- Decision (Task 12): the update download uses `node:http`/`node:https` and follows redirects itself, checking each address. Why: the end-to-end update crashed the app's server mid-download two times in three. Undici (fetch) in Electron 45's Node (24.22.1, undici 7.30.1) throws an uncaught `assert(!this.paused)` when a body that ends with the connection arrives faster than it is written. Cost if wrong: redirect handling is ours to keep right; tests cover relative, absolute, unsafe and looping redirects.
- Decision (Task 12): the unpacked-tree check walks with `process.noAsar` set. Why: under Electron, fs reads `app.asar` as a folder, so the app refused every genuine update ("would land outside its folder"), while the release check, under plain Node, passed the same zip. Cost if wrong: none; the walk is synchronous and puts the setting back.
- Decision (Task 12): an update whose signature carries no certificate (ad hoc, `codesign -s -`) is refused as "not signed by the same certificate", not as a certificate that "could not be read". Why: it is an app somebody else made, not a fault worth retrying. Cost if wrong: none.
